Spécification backend & architecture

Plateforme de commande B2B SIA. Architecture orientée événements : le logiciel de gestion existant du client (désigné ici YME) reste l'unique source de vérité pour les produits et le stock ; il diffuse, la plateforme reçoit. Aucun composant de la plateforme n'écrit dans le système existant, ni ne s'y connecte en base.

Version 2.0 Runtime Java 21 · Spring Boot 3.x Données PostgreSQL 16 Bus Apache Kafka Objets S3 / Cloudflare R2 Hébergement VPS Docker Statut À valider — 14 points ouverts

1 Portée & principes

Dans le périmètre

  • API REST de la plateforme B2B : authentification, catalogue, recherche, panier, commandes, compte client, back-office.
  • Passerelle d'ingestion événementielle recevant les changements de produits et de stock émis par YME.
  • Boîte d'émission (outbox) exposant les commandes validées pour récupération par le connecteur du client.
  • Projections locales produits / stock, réservations, historique de mouvements, réconciliation.
  • Supervision : santé des flux, retards d'ingestion, file d'erreurs, rejeu manuel.

Hors périmètre

  • Toute modification, extension ou requête directe dans YME ou sa base de données.
  • Le connecteur côté client (agent qui émet les événements depuis YME) — fourniture et responsabilité à arbitrer, voir §14.
  • Comptabilité, facturation légale, déclarations fiscales : restent dans YME.
  • Paiement en ligne — non prévu à ce stade (voir TBD-11).

Principes directeurs

P1 — YME est la source de vérité
Produits, prix de base, stock, clients et tarifs proviennent de YME. La plateforme ne fait qu'en tenir une projection lisible. Aucune donnée maîtresse n'est créée côté plateforme.
P2 — Découplage total
Aucune connexion synchrone vers YME sur le chemin critique d'une requête utilisateur. Si YME est arrêté, le site continue de servir le catalogue et d'enregistrer des commandes.
P3 — Pull uniquement vers le client
Rien n'entre dans le réseau du client à notre initiative. C'est le connecteur du client qui appelle la plateforme, dans les deux sens (dépôt d'événements, retrait de commandes).
P4 — Tout événement est rejouable
Chaque message reçu est conservé brut, identifié, horodaté. Un incident se répare par rejeu, jamais par correction manuelle en base.
P5 — Le stock projeté est une information, pas un engagement
La disponibilité affichée est une projection datée. L'engagement ferme sur les quantités est prononcé par YME à la confirmation de commande.
P6 — Contrat explicite et versionné
L'enveloppe des événements et les contrats API sont versionnés. Un schéma inconnu est rejeté et signalé, jamais interprété au mieux.
Dépendance client — bloquant conception

Les DTO et modèles de données Produit et Stock ne sont pas définis dans ce document. Ils doivent être fixés avec le client à partir des structures réelles de YME (noms de champs, types, cardinalités, unités, référentiels de codes), car la fidélité à 100 % de ces structures est la condition du fonctionnement événementiel. Ce document définit tout ce qui les entoure : enveloppe, transport, garanties, projections, cycle de vie. Voir §14 — TBD-01 à TBD-05.

3 Architecture haut niveau

Un seul déploiement Spring Boot, découpé en modules internes à frontières explicites. Pas de microservices : le volume attendu (≈48 000 références, quelques dizaines de clients professionnels) ne les justifie pas et ils multiplieraient les modes de panne sur un VPS unique. Le découplage passe par le bus d'événements Kafka, pas par la découpe en services.

Règles de dépendance entre modules

  • ingestion ne dépend d'aucun module métier. Il ne connaît que l'enveloppe et la table brute.
  • projection est le seul module autorisé à écrire dans les tables de projection produit / stock.

  • Aucun module n'ouvre de connexion vers le réseau du client (P3).

5 Modèle événementiel

5.1 Le principe, sans métaphore

YME émet un message chaque fois qu'une donnée qui nous concerne change : création ou modification d'un article, variation de stock, changement de tarif. La plateforme n'interroge jamais YME. Elle reçoit, enregistre, applique. Conséquences directes :

  • La charge du site n'atteint jamais YME. Mille visiteurs simultanés ne génèrent aucune requête sur le système existant.
  • Un arrêt de YME n'arrête pas le site : les projections restent servies, avec leur date de dernière mise à jour.
  • Un arrêt de la plateforme ne perd pas de données : le connecteur conserve les événements non acquittés et les rejoue.

5.2 Transport d'ingestion — options à arbitrer

Le mécanisme d'émission dépend de ce que YME sait faire. Les quatre options ci-dessous sont techniquement équivalentes pour la plateforme : notre passerelle reçoit la même enveloppe dans tous les cas. Le choix est une décision client (TBD-06).

OptionMécanisme côté clientLatenceCondition
A — Push directYME appelle notre endpoint à chaque changementImmédiateYME sait émettre du HTTP sortant
B — Table de sortie + agentDéclencheur SQL dans YME alimente une table de sortie ; un agent léger la lit et publie1–10 sAccès en écriture à un déclencheur / une table dans YME
C — Dépôt de fichiersYME exporte un fichier (CSV/XML/JSON) ; l'agent le dépose sur la passerelleSelon planificationExport existant. Le moins réactif, le plus simple.
D — Lecture en réplicaUn agent lit un réplica en lecture seule de la base YME et détecte les deltas5–60 sRéplica disponible. Aucune écriture dans YME.
Ce que nous refusons

Toute solution où la plateforme lit en direct la base de production de YME sur le chemin d'une requête utilisateur. C'est la seule architecture qui ferait porter la charge du site sur le système de gestion, et le motif même de ce projet est de l'éviter.

5.3 Enveloppe d'événement

5.5 Bus Kafka — topics et événements internes

Tout transport d'événement à l'intérieur de la plateforme passe par Kafka. La passerelle HTTP n'est qu'une porte d'entrée : elle écrit le message brut en base, puis un relais le publie sur le topic correspondant. Les projections et les effets de bord sont des consommateurs.

connecteur ─HTTP─► passerelle ─► event_inbox (Postgres) ─relais─► topic Kafka ─► consommateurs
                        │                                                    ├► projection produit
                 202 immédiat                                               ├► projection stock
                                                                            └► ops / supervision

Pourquoi les deux et pas Kafka seul à la réception : l'écriture en base rend l'accusé au connecteur indépendant de la disponibilité du courtier, porte l'unicité de eventId (contrainte SQL, garantie par le moteur) et conserve le journal consultable au-delà de la rétention Kafka. Kafka apporte le découplage, l'ordre par partition, la reprise par offset et le rejeu.

Ordre par entité

La clé de partition est l'identifiant d'entité. Tous les événements d'une même référence atterrissent donc sur la même partition et sont consommés dans l'ordre de publication. Le contrôle de entityVersion (5.7) reste en place : il couvre le désordre introduit avant Kafka, c'est-à-dire côté connecteur ou réseau.

5.6 Outbox sortante — commandes vers YME

Une commande validée n'est pas poussée vers le client : elle est déposée dans une boîte que le connecteur vient vider. Le sens de l'appel réseau reste toujours client → plateforme (P3). Ce sens sortant reste en HTTP et non en Kafka, délibérément : exposer un topic au réseau du client imposerait un client Kafka, un port ouvert et une gestion d'offset côté connecteur. Un appel HTTP authentifié avec accusé explicite est plus simple à exploiter et ne dépend d'aucune bibliothèque chez le client. Kafka reste interne à notre plateforme.

1
Dépôt transactionnelDans la même transaction que la validation de la commande, une ligne est écrite dans outbox_message (statut PENDING). Aucune commande validée ne peut exister sans son message.
2
RetraitLe connecteur appelle l'endpoint de lecture, qui renvoie jusqu'à N messages en attente et les marque LEASED avec une échéance.GET /ingest/v1/outbox?limit=50
3
Injection dans YMEHors de notre responsabilité. Le connecteur crée la pièce dans YME.
4
AccuséLe connecteur acquitte chaque message traité. Sans accusé avant échéance, le message redevient PENDING et sera re-servi : la remise est au moins une fois, l'injection côté client doit donc être idempotente sur orderNumber.POST /ingest/v1/outbox/ack
5
Retour d'étatLa confirmation revient comme un événement entrant ordinaire (order.acknowledged puis order.confirmed), traité par la même passerelle.

5.7 Garanties et mécanismes de sûreté

MécanismeImplémentation
IdempotenceContrainte d'unicité sur event_inbox.event_id. Un doublon renvoie 202 avec duplicate: true sans retraitement.
Durabilité avant traitementLa passerelle écrit l'événement brut en base et répond 202 sans attendre le courtier. La publication Kafka puis le traitement sont asynchrones : ni une indisponibilité de Kafka ni une erreur de projection ne peuvent faire échouer une réception.
Ordre de consommationPartitionnement par identifiant d'entité : les événements d'une même référence sont consommés dans l'ordre de publication, sans coordination applicative.
Progression des consommateursOffset validé manuellement après traitement réussi. Un redémarrage reprend au dernier événement non traité ; au pire un événement est retraité, ce que l'idempotence absorbe.
Ordre par entitéComparaison de entityVersion avec la version projetée. Inférieure ou égale = ignoré (SUPERSEDED), consigné.
Détection de trousSuivi du dernier sequence par source. Un saut lève une alerte et permet une demande de rejeu de l'intervalle manquant.
Reprise en erreurGestionnaire d'erreur Spring Kafka : 5 tentatives sur topics de reprise, délai exponentiel (10 s → 5 min), puis bascule sur <topic>.dlt. L'événement correspondant passe en DEAD dans event_inbox, apparaît dans la file d'erreurs du back-office et reste rejouable en un clic. Un message en rebut ne bloque jamais sa partition.
Réconciliationstock.snapshot quotidien planifié. Comparaison ligne à ligne avec la projection ; les écarts sont listés dans un rapport et corrigés par application du snapshot.
RétentionTopics Kafka : 7 jours, pour le rejeu immédiat. event_inbox : 90 jours en ligne, puis archivé en objet compressé (S3/R2). Un rejeu au-delà de 7 jours republie depuis la base, jamais depuis le courtier.

1

7
AffichageLe client voit la nouvelle disponibilité, avec l'âge de la donnée. Objectif de bout en bout : moins de 5 s en options A et B.

6.4 Média produit

Les images ne transitent pas par les événements. Le payload produit peut porter une référence de fichier ; le fichier lui-même est déposé par le back-office ou par un import de médias, stocké dans S3/R2 sous une clé dérivée de la référence, et servi via CDN en trois formats (miniature, fiche, zoom). Si YME détient les images, leur mode de transmission est à définir (TBD-08).

9 Règles métier

Réf.RègleStatut
RM-01Aucun compte ne peut commander avant validation manuelle par SIA (status = ACTIVE et rattachement à un client YME établi).Arrêté
RM-02Un utilisateur ne voit que les prix de son propre rattachement client. Aucun prix public sans session authentifiée.Arrêté
RM-03La plateforme ne crée, ne modifie et ne supprime jamais un produit, un stock ou un tarif. Ces données n'existent côté plateforme que par projection.Arrêté
RM-04Un produit sans prix résolu pour le client connecté n'est pas commandable : il s'affiche « prix sur demande » et le bouton d'ajout est inactif.Arrêté
RM-05Un produit INACTIVE reste accessible par son URL (historique, référencement) mais n'est pas commandable et disparaît des listes.Arrêté
RM-06La quantité commandée doit respecter le conditionnement de vente (multiple, minimum) porté par la projection produit.Dépend TBD-01
RM-07Toute soumission est précédée d'une revalidation. Un écart de prix ou de disponibilité interrompt la soumission et est présenté au client, qui doit accepter explicitement.Arrêté
RM-08Une commande soumise pose des réservations locales valables 48 h. À expiration sans validation, elles sont libérées et la commande reste soumise, signalée dans le back-office.Arrêté — durée ajustable
RM-09Le client peut annuler sa commande tant qu'elle est en SUBMITTED. Après VALIDATED, l'annulation passe par SIA.Arrêté
RM-10Une confirmation partielle de YME est un état normal : les quantités confirmées font foi, l'écart est notifié au client et au back-office, la commande passe PARTIALLY_CONFIRMED.Arrêté
RM-11La disponibilité affichée est accompagnée de son âge. Au-delà d'un seuil de retard d'ingestion, un avertissement explicite remplace la quantité.Seuil : TBD-07
RM-12Le dépassement d'encours ou de plafond de crédit ne bloque pas la commande côté plateforme ; il est signalé au back-office pour arbitrage.À confirmer — TBD-12
RM-13Les promotions plateforme ne peuvent jamais produire un prix inférieur à un plancher défini par SIA.Plancher : TBD-10
RM-14Les lignes de commande conservent un instantané du libellé et du prix. L'historique client est immuable.Arrêté

10.3 Cas limites d'intégration et parti pris

Deux stock.changed arrivent dans le désordreCelui dont entityVersion est inférieure ou égale à la version projetée est marqué SUPERSEDED et ignoré. Sans entityVersion, repli sur occurredAt (moins sûr — TBD).
Événement pour une référence inconnueCréée en projection avec status = ORPHANED, non publiée au catalogue, listée en supervision jusqu'à l'arrivée du product.upserted correspondant.
Stock projeté négatifAccepté et stocké tel quel (c'est l'état réel de YME), disponibilité plafonnée à 0 à l'affichage, alerte levée.
Commande sur une donnée périmée (survente)Assumé par conception : la plateforme n'engage pas le stock. YME confirme partiellement et le client est notifié (RM-10). Le tampon de sécurité réduit la fréquence du cas.

Connecteur qui rejoue tout son historiqueAbsorbé par l'idempotence sur eventId. Les doublons sont acquittés sans effet ni charge de projection.
Commande remise deux fois au connecteurRemise au moins une fois assumée. L'injection côté YME doit être idempotente sur orderNumber — exigence à porter au connecteur.

Prix changé entre l'ajout au panier et la soumissionBlocage à la revalidation avec affichage des deux prix. La soumission exige une acceptation explicite (RM-07).
Plusieurs dépôts / magasins dans YMELe modèle de projection prévoit une clé de dépôt. Faut-il agréger ou exposer par dépôt : TBD-02.
Courtier Kafka indisponibleLa réception continue : les événements s'accumulent en base et le connecteur reçoit ses 202. Le relais reprend la publication au rétablissement, dans l'ordre. Alerte sur kafka.relay.unpublished.
Un message empoisonne un consommateurTentatives sur topic de reprise, puis bascule en DLT. La partition n'est jamais bloquée : les autres références continuent d'être projetées.
Rétention Kafka dépassée pendant un incident longLe rejeu republie depuis event_inbox (90 jours). Le courtier n'est jamais la source de vérité d'un rejeu.
Snapshot contredisant les événements incrémentauxLe snapshot fait foi. Les écarts sont consignés dans le rapport de réconciliation et notifiés.
Base de la plateforme restaurée après incidentRejeu depuis event_inbox (90 j) puis application du dernier snapshot. Les commandes sont rétablies depuis la sauvegarde ; les messages d'outbox non acquittés sont re-servis.
